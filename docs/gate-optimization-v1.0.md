## 二、核心问题诊断

### 问题1：门禁过载——54项检查分散在4个模块

**证据**：
- gate-check（7项）+ train-check（8项）有4项完全重复（H8/H9/禁用词/元话语）
- REVIEW.md（27项）与上述有语义重叠
- G7发布前清单（12项）与前面模块有隐式重复
- 主笔每次交稿跑2-3个脚本

**影响**：返工循环（gate过→train挂→改完→gate重跑）、责任稀释、版本不一致

### 问题2：H14 AI味检测在政策类稿件误报率高

**证据**：
- 选题⑤实测：18分→9分→5分，改了3轮
- 扣分项：顿号罗列（"算力、网络、数据"）、翻案腔（"不是技术讨论而是国家战略"）、翻译腔（"这意味着"）
- 政策类稿件这些特征**不可改**（官方列举必须用顿号、政策定调必须用翻案腔）

**影响**：主笔陷入"删了失实、留了扣分"两难；审核岗反复人工豁免

### 问题3：结构多样性G8门禁执行弱

**证据**：
- 5篇稿件中4篇用序数词骨架
- G8只给WARN不阻断
- 无替代模板库供主笔参考

### 问题4：门禁反馈滞后

**证据**：
- humanizer-check只给分数不给改写建议
- 写完才知道AI味超标，此时结构已定型
- 修改成本：18分→5分需要3轮改稿

## 三、优化方案（按优先级排序）

### 🔴 P0：合并重复检查，统一入口

**动作**：
1. gate-check.py 成为**唯一自动化门禁入口**
2. train-check.py 降级为"训练集抽检工具"，不再参与稿件门禁
3. G8结构多样性整合进gate-check主流程（不再独立脚本）
4. 建立单一禁词库文件，gate-check和REVIEW.md共用

**预期收益**：主笔从跑3个脚本降为1个；检查项从54项降至30项以内

**工作量**：2-3人日

### 🔴 P0：H14 AI味检测增设行业豁免

**动作**：
1. humanizer-check.py 新增 `--policy-mode` 参数
2. 政策类稿件自动豁免：顿号罗列（规则2）、翻案腔（规则1）、冒号空转（规则5）
3. 其余规则照常执行
4. 触发条件：标题或首段含政策关键词（"方案""条例""通知""意见""办法"）
5. REVIEW.md注明豁免依据，避免滥用

**预期收益**：政策类稿件不再陷入3轮改稿循环

**工作量**：20行代码改动，2-3小时

### 🟠 P1：建立三级门禁架构

**动作**：

```
第一层：自动化门禁（gate-check.py）
  职责：可机械检查的硬性规则
  检查项：H8字数 / H9段落≤3句 / 禁用词 / 元话语 / 注入残留 / G8结构多样性
  阻断：BLOCK（字数<200/注入/元数据）+ WARN（其余）

第二层：人工复核（审核岗）
  职责：主观判断、语境理解
  检查项：R1-R6致命红线 / H14 AI味 / 金句密度 / 结构合理性
  阻断：红线项FAIL=撤稿，其余=协商

第三层：发布终检（G7清单）
  职责："能不能发"的最终确认
  检查项：12项清单（标题/封面/金句/防盗链/互动/AI味/OCR/pre-mortem/群发开关）
  阻断：任一FAIL=不能发
```

**关键原则**：
- 自动化层不处理主观判断（H14移到人工层）
- 人工层不重复自动化层已检查项
- 发布终检只做"最终确认"，不做新检查

### 🟠 P1：H14升级为"可解释性评分"

**动作**：
1. humanizer-check.py 输出格式升级：不只给分数，还输出**扣分点分布图**（哪段扣分、哪条规则命中、替代表达建议）
2. 允许主笔在"结构说明"中备注"序数词为政策格式要求"，门禁自动放行
3. 提供"同义改写库"：对不可删的术语给出替换选项

**预期收益**：主笔从"猜怎么改"变为"知道改哪里、怎么改"

### 🟡 P2：前置预防机制

**动作**：
1. 在gate-check.py中增加"AI味风险预检"模式：只检测不扣分，写作中实时提示
2. 建立结构变体模板库（替代序数词骨架的6种方案B-F）
3. 分级放行：重点稿件全量检查 / 常规稿件只查H8/H9/禁用词 / 实验稿放宽H9

**预期收益**：返工率降低40%+

## 四、争议项裁决

| 争议项 | 裁决 | 理由 |
|--------|------|------|
| H9段落≤3句是否升级BLOCK | **保留WARN** | BLOCK过多会导致主笔"为过审而拆段"，牺牲内容连贯性 |
| G8结构多样性是否升级BLOCK | **保留WARN+首篇豁免** | BLOCK会强制阻断政策类稿件（天然用序数词结构）|
| H14判定方式 | **保留自动+加白名单** | 移到人工层会丧失一致性，加白名单解决政策类误报 |

## 六、各视角评审摘要

### 主编视角（Agnes 2.5 Flash）
- 核心：问题不是"检查不够严"而是"检查太乱"
- 建议：先做减法（合并）→再做分层（明确职责）→最后做预防（前置约束）
- 预期：1个月内门禁效率提升50%

### 审核视角（DeepSeek V4 Flash）
- 核心：H14在政策类稿件误杀合规稿件，规则公信力下降
- 建议：增设行业豁免清单 + H9/G8升级BLOCK + 合并为一键预检
- 成本：低（20行代码）/ 中（2-3小时）/ 中（100行封装脚本）

### 技术视角（Agnes 2.5 Flash）
- 核心：gate-check与train-check逻辑分散，维护成本高
- 建议：构建统一check-engine.py + 三级闸门（硬阻断/软告警/降级）+ 补齐G7自动化缺口
- 工作量：2-3人日 / 1-2人日 / 5-7人日

### 主笔视角（DeepSeek V4 Flash）
- 核心：门禁反馈滞后，改写成本高，规则与内容冲突
- 建议：写作中嵌入轻量级预检 + 政策豁免参数 + H14改为可解释性评分
- 优先级：P0（预检）→ P1（豁免）→ P2（创作压力）
